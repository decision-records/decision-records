# 分阶段引入极限编程

* 状态：征求意见
* 日期：2025-10-06
* 决策者：工程负责人（待确认）
* 负责人：工程经理

摘要：进行中。这是一个起点，供正在考虑如何引入极限编程（XP）实践（如测试驱动开发、结对编程、持续集成和小版本发布）的工程团队参考。它展示团队如何界定问题、辩论各项方案并收集信息。它不记录任何决策。

## 问题

产品团队以大批量交付功能，晚发现的缺陷代价高昂：相当比例的版本在发布后需要紧急修复。工程领导者对极限编程的实践感兴趣，这是一种强调技术实践的敏捷软件开发方法，如测试驱动开发、结对编程、持续集成、小版本发布、重构和代码集体所有权。

这些实践相互支持，但也会改变工程师每天的工作方式。一次性全部采用，很可能遇到阻力并流于表面。需要回答的问题：

* 我们想解决哪些问题（缺陷发现太晚、反馈慢、知识集中在少数人手中），哪些实践针对这些问题？
* 实践应按什么顺序引入，谁先开始？
* 我们将度量什么，以知道这些实践有帮助？
* 在共同标准与各团队自行选择之间，怎样的平衡才合适？

## 假设

每条假设都需要检验。

* **晚发现的缺陷主要是因为缺少快速的自动化反馈。** 检验：把一份紧急修复样本追溯到本可发现缺陷的环节。
* **基础实践（持续集成和自动化测试）使其他实践成为可能。** 检验：询问尝试过的团队，哪些实践依赖哪些实践。
* **工程师会采用他们在邻近团队里看到有效的实践。** 检验：问他们什么能说服自己，什么令自己担忧。
* **发布后的紧急修复率是衡量进展的公平标准。** 检验：约定如何计数，并检查其他度量（变更前置时间、变更失败率）是否讲述了不同的故事。

## 约束

* 团队在学习期间仍需交付功能，因此第一阶段的产出很可能偏低。
* 工程师应保留如何结对以及使用什么工具的选择权。
* 现有的构建和测试基础设施在持续集成发挥作用之前可能需要改进。
* 未知，待确认：今天有多少代码可测试，以及监管或客户方面的约束是否影响发布频率。

## 考虑过的方案

对每个方案，估计价值、成本、时间安排和所需能力，并记下哪些证据会让团队改变想法。

* **在每个团队同时采用所有实践。**
  * 价值：各实践相互强化。
  * 成本驱动因素：培训；学习期间交付变慢；所有团队同时进行的工具工作。
  * 风险：变化很大；缺乏基础技能的团队可能在几周内放弃。
* **按选定的顺序，逐个团队引入实践。** 例如先是持续集成和自动化测试（基础），然后是小版本发布和结对编程，再然后是测试驱动开发。
  * 价值：每项实践都有时间沉淀；先行的实践让后续成为可能；第一个团队的经验指导其余团队。
  * 成本驱动因素：辅导；纳入计划的结对和写测试的时间；交付流水线的基础设施工作。
  * 时间安排形态：先后相继，下一个团队在前一个团队保持发布流水线健康达到规定期限后加入。
  * 所需能力：一名教练；可靠的构建流水线；管理者对产出下降的支持。
  * 风险：慢；各实践采用得不均衡。
* **只采用容易的实践。** 投入少，但可能漏掉收益最大的实践，如自动化测试。
* **采用另一套实践**（例如 DORA 关于软件交付绩效的研究所描述的，如持续交付、主干开发和松耦合架构），并把 XP 视为多个来源之一。
* **不做任何新的事**，直接处理缺陷的具体成因。一个真实的基准。

## 论证

团队应预料到的争论点：

* **结对编程。** 许多工程师对此持怀疑态度。它在哪里有帮助（知识共享、复杂工作），在哪里没有？
* **标准化，还是让团队自己选择？** 共同的结果（更少的紧急修复、更快的反馈），团队在如何达成上有自由，还是更严格的标准？
* **短期的质量与速度。** 领导者是否愿意在团队学习期间接受较低的产出？
* **TDD 是手段还是目的？** 有些实践（如测试驱动开发）即使在有经验的从业者之间也有争议。团队应在采用某项实践之前先决定它解决什么问题。

团队可以如何评估成本与权衡：

1. 为现有做法估价：花在紧急修复上的精力、晚发现缺陷造成的延误、对客户的影响。按组织自己的说法使用区间。
2. 为计划估价：辅导、培训、结对和测试的时间、流水线的基础设施，以及交付的暂时下降。
3. 先选定度量：需要紧急修复的版本占比、变更前置时间、部署频率、服务恢复时间（DORA 度量），以及工程师的反馈。
4. 在最好、最可能和最差情景下比较各方案；问如果收益来得更晚或比预期更小，答案会怎样变化。
5. 使用加权矩阵和事前验尸。

## 决策

**尚未决定。** 这是一个起点。使用它的团队应以自己的决策取代本节。

建议的决策方式：

* 确认由谁决策以及何时决策。
* 先就标准和权重达成一致。
* 收集上述证据并记录发现。
* 分发征求意见，然后做出决策并更新状态。

## 影响

如果团队选择分阶段的做法，就需要：

* 指定一名教练，并请第一个团队如实报告什么有帮助、什么没有。
* 在交付计划中安排结对和写测试的时间。
* 在依赖构建和测试流水线之前先投资建设它。
* 约定一条停止规则：如果某项实践在规定期限后没有帮助，团队可以提议停止并记录原因。
* 让工程师保留如何结对和使用何种工具的选择权；实践确定结果，而不是确定达成结果的每个细节。
