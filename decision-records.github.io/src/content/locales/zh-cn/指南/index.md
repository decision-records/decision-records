## 什么是决策记录？

**决策记录（DR）** 记录一项重要的选择：促成它的情形、权衡过的备选方案、最终做出的选择，以及预期的后果。**决策日志（DL）** 则是一个团队、职能或组织全部决策记录的持续汇编，实际上就是一份“我们为什么这样做”的组织记忆。

决策记录不是：

* 会议纪要（记录的是 *讨论了什么*，而不是 *决定了什么以及为什么*）。
* 项目计划（记录的是 *接下来做什么*，而不是 *为什么选这条路而不选其他路*）。
* 政策文件（记录的是 *长期有效的规则*，尽管决策记录常常会产生这样的规则）。

它介于这几者之间：一份简短而持久的文件，其存在的目的就是让一项选择背后的理由比做出选择的那场会议活得更久。

## 为什么领导者（而不只是工程师）应当使用决策记录

软件团队最先采用这项实践，因为代码很难撤回，而且新工程师总会问“这为什么是这样构建的？”每一位领导者面对的其实是完全相同的情形：

* **组织记忆会随人离开。** 当选定现行销售区域模式的销售副总裁离职时，如果没有写下来，他的理由也随之消失。
* **重组和领导层更替会引发重复争论。** 没有记录，新任领导者要花几周时间重新辩论一个早已审慎做出的决策，更糟的是，在不了解它为何存在的情况下就把它推翻。
* **有了“为什么”，而不只是“是什么”，入职会更快。** 新员工如果能读到本职能最近的十几项决策，就能理解组织的判断，而不只是它当前的状态。
* **写下来本身就能改进决策。** 在决定之前，把背景、备选方案和权衡写到纸面上，会暴露口头讨论容易忽略的空白和未说明的假设。
* **它在不增加官僚作风的情况下建立问责。** 决策记录写明由谁在何时做出决定以及原因，这既保护决策者（有据可查、理由充分的选择），也保护组织（情况变化时有明确的负责人来复议）。
* **它让沟通跨越距离与时间。** 对远程和异步协作的团队，以及不在现场的利益相关方，一份写得好的决策记录能替代原本需要重复召开的会议。

这一切并不只属于软件领域。它适用于 *任何* 难以撤销、影响决策者以外的人，或日后很可能被质疑的决策。

## 决策记录适用于企业的每一个部分

把“决策记录”看作一种体裁，而不是某个部门的工具。无论决策是架构方面的还是商业方面的，同样的六部分结构都适用：

* **战略决策记录**：进入或退出市场、竞争姿态、多年期的押注。
* **销售决策记录**：区域设计、薪酬方案、CRM 与工具选择、渠道策略。
* **营销决策记录**：品牌定位、渠道组合、外包机构还是内部团队、定价沟通。
* **产品决策记录**：定价模式、路线图取舍、自建还是外购、停止服务的决策。
* **项目决策记录**：交付方法、供应商选择、范围取舍。
* **风险决策记录**：风险的接受、缓解、转移或规避，及其理由。
* **人力资源决策记录**：政策变更（远程办公、职级、薪酬带宽）、组织设计。
* **公共关系决策记录**：危机沟通姿态、发言人政策、媒体互动规则。
* **专业发展决策记录**：培训投入、晋升标准、继任选择。
* **以用户为中心的设计决策记录**：研究方法选择、无障碍取舍、用户体验方向。
* **软件架构 / 工程决策记录**：最初的用例：技术、平台和设计选择。

[示例](../示例/index.md)目录中有大多数这些领域的实际样例。许多组织先把决策记录用于工程，后来发现战略、人力资源或销售团队也想要完全相同的做法。常常是团队只是把这项实践称为“决策”而不是“决策记录”，这样它对非技术团队来说就显得自然，而不是从工程那里借来的，这时他们才恍然大悟。

## 决策记录的结构

[template/index.md](../模板/index.md) 中有两个模板：用于日常决策的**轻量**六字段版本，以及用于高风险、高关注度决策的**完整**版本。两者的核心逻辑相同：

1. **标题**：用简短的现在时主动句陈述决策本身（例如“采用季度 OKR”，而不是“OKR 讨论”）。尽量控制在 50 个字符以内。
2. **状态**：决策处于生命周期的哪个位置：征求意见、已提议、已接受、已否决、已弃用或已被取代。
3. **背景（问题）**：使这项决策成为必要的情形、各种力量和约束。要写得让一位不记得那场会议的读者也能明白，这个问题为什么会出现。
4. **考虑过的方案（立场）**：现实可行的备选方案，以事实和权衡的方式陈述，而不是为了让被选方案显得理所当然而摆出的稻草人。如果有人问“你们考虑过 X 吗？”，而记录中没有答案，那这份记录就是不完整的。
5. **决策**：选择本身，用平实、主动的语言：“我们将做 X。”不是优缺点的概括，而是对所选内容的清晰陈述。
6. **后果（影响）**：由此带来的变化，包括成本、风险、后续决策，以及因未选择其他方案而放弃的东西。好的后果读起来是“我们现在做 X 而不是 Y”，而不是对已做出的决策重述一遍优缺点。

完整模板增加了适用于高风险决策的字段：**假设**、**约束**、**意见**（谁提出了什么建议及原因）、**相关的决策 / 需求 / 工件 / 原则**，以及为需要更深入审视的决策准备的结构化分析小节（成本分析、SWOT、PEST）。

## 决策记录的生命周期

一份决策记录通常经历五个阶段：

**发起 → 调研 → 评估 → 决定 → 维护（→ 终止）**

* *发起*：有人认定某项选择足够重要，值得写一份记录，并开启一份草稿。
* *调研*：收集备选方案、约束和假设，并征询利益相关方的意见。
* *评估*：把记录发出来征求意见，通常设定一个时间盒（一周是常见的默认值）。
* *决定*：决策者（个人或小组，依你的治理模式而定）接受、否决，或退回补充工作；状态随之更新。
* *维护*：记录保持可被发现，并在情况发生实质性变化时重新审视。
* *终止*：如果被取代，旧记录的状态改为“已被取代”，并链接到新记录。旧记录绝不删除，这段历史正是意义所在。

## 角色与治理

对每份决策记录，请写明：

* **负责人 / 提议人**：起草记录并推动其作出决策。
* **决策者**：有权接受它的人、角色或委员会。请针对每一类决策明确说明（例如“定价变更：产品副总裁；进入市场：CEO + 董事会”）。
* **贡献者**：其意见实质性地影响了备选方案或权衡的人。
* **此后的责任人**：负责维护该决策、定期复审（每年一次是常见的节奏），并负责最终将其废止的人。

下列治理问题值得为你的组织一次性书面确定（另见[检查清单](../检查清单/index.md)）：

* 谁可以 *提出* 决策记录？（通常：任何人。）
* 谁可以 *批准*，批准权是否因决策类型或金额 / 风险门槛而不同？
* 出现僵局或分歧时由什么来解决：共识、指定的批准人，还是逐级上报？
* 记录被接受后可以改动到什么程度？许多团队偏好“活文档”模式：新信息带着时间戳追加进去，而不是悄悄改写历史。

## 最佳实践

* **一份记录只对应一项决策。** 不要把几项选择捆在一份文件里，否则日后无法引用、取代或检索。
* **保持简洁。** 一页，而不是一份报告。如果超过一页，这项决策很可能不止是一项决策。
* **为陌生人写背景。** 假设读者没有会议上的任何共同背景，两年后同样不会有。
* **用主动语态陈述决策。** “我们将迁移到 X”，而不是“X 被视为首选方向”。
* **把后果写成发生了什么变化，而不是优缺点。** 权衡的争论属于“考虑过的方案”；“后果”讲的是接下来会发生什么。
* **把记录存放在团队本来就工作的地方。** 版本控制下的 `decisions/` 文件夹、维基空间或共享盘文件夹，最好的存放位置就是你的团队真正会打开的那个。
* **把决策记录留给难以撤销、横跨多个领域或日后很可能被质疑的决策。** 并非每项选择都需要一份，参见[检查清单](../检查清单/index.md#检查清单这项决策需要决策记录吗)。
* **用取代代替悄悄删除。** 当决策改变时，写一份新记录，并链接回它所取代的那份。

## 常见误区

* **变成事后补办的文书工作。** 如果决策记录是为了给已经做出并宣布的选择辩护而写的，它的大部分价值就丧失了：重点是在承诺 *之前* 磨炼思考，而不是事后生成一份合规文件。
* **日志疲劳。** 记录每一个小选择会把重要的淹没，并让人们不再阅读日志。只为真正难以撤销或影响广泛的决策写记录。
* **写成优缺点而不是决策。** 一份以权衡清单结尾而没有明确“我们将做 X”的记录，不是决策记录，而是一份备选方案备忘录。
* **没有负责人。** 没有指定决策者或复审人的决策记录往往会逐渐过时，并失去信任。
* **把模板当成官僚程序，而不是检查清单。** 模板的价值在于它是良好思考和良好沟通的检查清单，而不是为填表而填表。

## 在你的组织中起步

1. 选一个职能或团队，找一项已经有争议或难以撤销的决策。
2. 用[轻量模板](../模板/index.md#轻量模板)起草这一项决策。
3. 与实际的决策者和利益相关方沟通，并为反馈设定时间盒。
4. 把它存放在持久且易于发现的地方。
5. 一旦这项实践证明有用，就建议把它作为团队的轻量标准，而不是自上而下的强制要求。决策记录最有效的时候，是团队因为它让自己的工作更轻松而采用它，而不是作为被迫的文书工作。
