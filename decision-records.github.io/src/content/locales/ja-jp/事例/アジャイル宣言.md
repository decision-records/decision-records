# アジャイル宣言

* ステータス: コメント募集中
* 日付: 2026-02-16
* 意思決定者: 最高技術責任者（CTO）（要確認）
* オーナー: デリバリー責任者

概要：作業中です。これは、アジャイル宣言の価値と原則を、デリバリーチームの計画と働き方にどう取り入れるかを検討しているチームの出発点です。チームが問いをどのように設定し、選択肢を議論し、情報を集めるかを示します。決定は記録されていません。

## 課題

デリバリーチームは現在、スコープが固定された長い計画型のプロジェクトで働いており、分析、構築、テストの間で引き継ぎが行われています。リリースは頻繁ではなく、顧客はしばしば、もはや自分のニーズに合わないものを受け取ります。リーダーは、アジャイル宣言の価値と原則、すなわち個人と対話、動くソフトウェア、顧客との協調、変化への対応に関心を持っています。

チームはまた、「アジャイル変革」が、その根底にある変化を伴わずにセレモニーだけが押しつけられると、しばしば失敗することも認識しています。答えるべき問い：

* 私たちはどんな問題を解決しようとしており、それが解決されたことをどう知るか？
* 宣言の価値は、私たちの製品、顧客、契約、規制に合うか。それとも一部だけか？
* 会議の名前だけでなく、行動が変わるように、価値をどう導入するか？
* 誰が最初に行い、行わないチームはどうなるか？

## 前提

それぞれの前提は検証すべきものです。

* **より短いフィードバックループは、私たちの顧客の役に立つ。**検証：顧客とデリバリーチームに、動くソフトウェアをどのくらいの頻度で見たいか、現在それを妨げているものは何かを尋ねる。
* **志願したチームは、実質的に価値を採用する。**検証：志願者が実際に何を変えたいか、スポンサーがいるかを調べる。
* **私たちの契約とガバナンスは、より頻繁で小さなリリースを許容する。**検証：頻繁なデリバリーを妨げているものについて、契約条件、承認、コンプライアンスの手順を確認する。
* **頻繁に届けられる動くソフトウェアは、進捗の妥当な尺度である。**検証：それをどう観察するか（アイデアから顧客までの時間、リリース頻度、顧客のフィードバック）を合意する。

## 制約

* スコープ固定の契約における顧客へのコミットメントは自動的には変えられない。それぞれに別個の話し合いが必要になる。
* 組織はおそらく、しばらくの間、2 つの働き方を並行して運用する。
* チームは、学びながらもデリバリーを続けなければならない。
* 不明、要確認：コーチングやトレーニングの予算、特定のライフサイクルを前提とする規制上または監査上の手順。

## 検討した選択肢

各選択肢について、価値、コスト、タイムライン、必要な能力を見積もり、どのような証拠がチームの考えを変えるかを書き留めます。

* **決まった開始日から、すべてのチームに1つのアジャイル手法を義務づける。**
  * 価値：一貫性と、リーダーシップからの明確なシグナル。
  * コスト要因：全員へのトレーニング。役割の変更。ツールの変更。チームが適応する間に失われる時間。その手法が一部のチームにはまったく合わないことを後で知るコスト。
  * タイムラインの形：開始は速く、軌道修正の長い尾が続く。
  * リスク：変化を伴わないセレモニー。準備のできていない人々が、働き方を変えずにそれを演じる。
* **志願者から始め、チームごとに採用する。**試したいチームが短いサイクルでリリースし、自分たちに合うプラクティスを選び、成果を示す。宣言の価値が指針となる。
  * 価値：実際の現場の事例。価値に結びついたプラクティス。
  * コスト要因：コーチングの時間。2 つの働き方の運用。学んだことを集めて共有する労力。
  * タイムラインの形：波状。先行チームが成果を示すだけ十分に運用された後に、次の波が加わる。
  * 必要な能力：スポンサー。成果を測定する方法。コーチングできる人。
  * リスク：採用にばらつきが出る。志願者は組織全体の典型ではない。
* **外部のコーチング組織を招き入れて、変革を主導させる。**
  * 価値：経験とスピード。
  * コスト要因：報酬。依存のコスト。契約が終わったときに去る知識。
  * リスク：能力が社内に残らないかもしれない。
* **より広い価値は採用せず、選んだプラクティス（たとえば短いサイクルと定期的なふりかえり）だけを採用する。**安上がりだが、根底の問題が解決されないままになるかもしれない。
* **現在のアプローチを維持し**、特定のデリバリーの問題を直接解決する。本物のベースライン。

## 論拠

チームが想定すべき論点：

* **手法かマインドセットか。**宣言は、特定の手法ではなく、価値と原則の集まりである。チームは手法（スクラム、カンバン、エクストリームプログラミングなど）の中から選ぶ。チームにどれだけの選択を与えるべきか？
* **固定スコープか変化への対応か。**既存の契約と予算は、チームにできることをどこまで制約するか？
* **誰が何で評価されるか。**チームが依然として計画の遵守で評価されるなら、頻繁な変更はリスクに感じられる。
* **展開の速さか深さか。**ゆっくり進めることで何を失い、速く進めることでどんなリスクを負うか？

チームがコストとトレードオフを評価する方法：

1. 組織自身の言葉で選択肢のコストを見積もる：トレーニングとコーチングの時間、役割の変更、ツールの変更、契約の再交渉、移行中の生産性の低下。単一の数字ではなく範囲を示す。
2. 始める前に成果指標を選ぶ：アイデアから顧客の手元に動くソフトウェアが届くまでの時間、リリース頻度、リリース後に見つかる欠陥、顧客のフィードバック、チームの満足度。セレモニーを数えるのは避ける。
3. 最良、可能性が高い、最悪のシナリオで選択肢を比較し、頓挫した場合に組織が最も良い立場にある選択肢はどれかを問う。
4. 価値、コスト、リスク、スピード、契約との適合、必要な能力について、重み付け意思決定マトリクスを使う。
5. プリモーテムを行う：変革が失敗したと仮定し、その理由を書き出す。

## 影響

チームがチームごとのアプローチを選ぶなら、次のことが必要になります。

* スポンサーと、志願したチームが学んだことを集める人を指名する。
* どのチームが、どの順序で、なぜ次に進むのかを公然と述べ、後から進むチームが取り残されたと感じないようにする。
* 各契約が更新の時期を迎えたときに、固定スコープのコミットメントをどう扱うかを決める。
* 停止のルールを合意する：先行チームが定めた期間の後に改善を示さなければ、一時停止して学んだことを記録する。
* プラクティスは、宣言の価値の範囲内で、各チームの選択として扱う。
