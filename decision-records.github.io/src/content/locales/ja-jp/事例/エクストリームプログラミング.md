# エクストリームプログラミング

* ステータス: コメント募集中

* 意思決定者: エンジニアリング責任者（要確認）

概要：作業中です。これは、テスト駆動開発、ペアプログラミング、継続的インテグレーション、小規模なリリースなど、エクストリームプログラミング（XP）のプラクティスを導入する方法を検討しているエンジニアリングチームの出発点です。チームが問いをどのように設定し、選択肢を議論し、情報を集めるかを示します。決定は記録されていません。

## 課題

プロダクトチームは機能を大きなバッチで出荷しており、遅れて見つかる欠陥は高くつきます。リリースの少なくない割合が、リリース後に緊急の修正を必要としています。エンジニアリングのリーダーは、テスト駆動開発、ペアプログラミング、継続的インテグレーション、小規模なリリース、リファクタリング、コードの共同所有といった技術的プラクティスを重視するアジャイルなソフトウェア開発手法、エクストリームプログラミングのプラクティスに関心を持っています。

これらのプラクティスは互いを支え合いますが、エンジニアの日々の働き方も変えます。すべてを一度に採用すれば、抵抗に遭い、表面的にしか行われない可能性が高いでしょう。答えるべき問い：

* 私たちはどの問題（遅れて見つかる欠陥、遅いフィードバック、少数の人が握っている知識）を解決したいのか。どのプラクティスがそれに対処するか？
* プラクティスはどの順序で導入すべきか。誰が最初に行うか？
* プラクティスが役立っていることを知るために、何を測定するか？
* 共有の標準と、各チームの選択のバランスは、どうあるべきか？

## 前提

それぞれの前提は検証すべきものです。

* **遅れて見つかる欠陥は、主に高速な自動フィードバックの欠如が原因である。**検証：緊急修正のサンプルを、欠陥を捕捉できたはずの場所まで遡って辿る。
* **基盤となるプラクティス（継続的インテグレーションと自動テスト）が、他を可能にする。**検証：プラクティスを試したチームに、どれがどれに依存していたかを尋ねる。
* **エンジニアは、隣のチームで機能しているのを見たプラクティスを採用する。**検証：エンジニアに、何があれば納得するか、何が不安かを尋ねる。
* **リリース後の緊急修正の割合は、進捗の妥当な尺度である。**検証：どう数えるかを合意し、他の指標（リードタイム、変更失敗率）が違う話をしていないかを確認する。

## 制約

* チームは、学びながらも機能を届けなければならないので、最初の期間のアウトプットはおそらく低くなる。
* エンジニアは、どうペアを組むか、どのツールを使うかについての選択を保つべきである。
* 継続的インテグレーションが役に立つ前に、既存のビルドとテストのインフラに手を入れる必要があるかもしれない。
* 不明、要確認：今日、コードベースのどれだけがテスト可能か、規制上または顧客上の制約がリリース頻度に影響するかどうか。

## 検討した選択肢

各選択肢について、価値、コスト、タイムライン、必要な能力を見積もり、どのような証拠がチームの考えを変えるかを記録します。

* **すべてのチームで、すべてのプラクティスを一度に採用する。**
  * 価値：プラクティスが互いを強化する。
  * コスト要因：トレーニング。学習中のデリバリーの遅れ。すべてのチームで同時に行うツールの作業。
  * リスク：大きな変更。基礎となるスキルのないチームは、数週間でプラクティスを放棄するかもしれない。
* **選んだ順序で、チームごとにプラクティスを採用する。**たとえば、まず継続的インテグレーションと自動テスト（基盤）、次に小規模なリリースとペアプログラミング、その後にテスト駆動開発。
  * 価値：各プラクティスが定着する時間がある。先のものが後のものを可能にする。最初のチームの経験が残りを導く。
  * コスト要因：コーチング。ペアリングとテスト作成の時間を計画に組み込むこと。パイプラインのインフラ作業。
  * タイムラインの形：順次。前のチームがリリースパイプラインを定めた期間健全に保ったときに、次のチームが加わる。
  * 必要な能力：コーチ。信頼できるビルドパイプライン。アウトプットの落ち込みに対するマネージャーの支援。
  * リスク：遅い。プラクティスの採用にばらつきが出る。
* **簡単なプラクティスだけを採用する。**労力は少ないが、自動テストのような最も便益の大きいものを飛ばしてしまうかもしれない。
* **別のプラクティスの組み合わせを採用し**（たとえば、継続的デリバリー、トランクベース開発、疎結合なアーキテクチャのような、ソフトウェアデリバリーに関する DORA の研究が述べるもの）、XP をいくつかある情報源の 1 つとして扱う。
* **新しいことは何もせず**、欠陥の個々の原因に直接対処する。本物のベースライン。

## 論拠

チームが想定すべき論点：

* **ペアプログラミング。**多くのエンジニアが警戒するプラクティス。どこで役に立ち（知識共有、複雑な作業）、どこで役に立たないか？
* **標準化か、チームの選択か。**共有された成果（緊急修正の減少、より速いフィードバック）と、そこへ至る方法にチームの自由を認めるか、それとも、より厳格な標準か？
* **短期的な品質かスピードか。**チームが学ぶ間、リーダーはアウトプットの低下を受け入れるか？
* **TDD は手段か目的か。**テスト駆動開発のようなプラクティスは、経験豊富な実践者の間でも議論がある。チームは、採用する前に、そのプラクティスがどんな問題に対処するのかを決めるべきである。

チームがコストとトレードオフを評価する方法：

1. 現在のアプローチのコストを見積もる：緊急修正に費やした労力、遅れて見つかる欠陥による遅延、顧客への影響。組織自身の言葉で、範囲を使う。
2. プログラムのコストを見積もる：コーチング、トレーニング、ペアリングとテストの時間、パイプラインのインフラ、一時的なデリバリーの落ち込み。
3. 先に指標を選ぶ：緊急修正を必要とするリリースの割合、変更のリードタイム、デプロイ頻度、サービス復旧までの時間（DORA の指標）、そしてエンジニアのフィードバック。
4. 最良、可能性が高い、最悪のシナリオで選択肢を比較する。便益が期待より遅く、または小さく現れた場合に答えがどう変わるかを問う。
5. 重み付けマトリクスとプリモーテムを使う。

## 影響

チームが段階的なアプローチを選ぶなら、次のことが必要になります。

* コーチを指名し、最初のチームに、何が役に立ち、何が役に立たなかったかを率直に報告してもらう。
* ペアリングと、デリバリー計画へのテスト作成のための時間を計画する。
* ビルドとテストのパイプラインに頼る前に、投資する。
* 停止のルールを合意する：定めた期間の後もプラクティスが役に立たなければ、チームはその停止を提案し、理由を記録できる。
* エンジニアに、どうペアを組むか、どのツールを使うかの選択を残す。プラクティスは成果を定めるべきであり、そこへ至る方法のすべての詳細を定めるものではない。
