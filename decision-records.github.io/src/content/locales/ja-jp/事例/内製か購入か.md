# プロジェクトの内製か購入か

* ステータス: コメント募集中
* 日付: 2026-06-01
* 意思決定者: COO（要確認）
* オーナー: オペレーション部長

概要：作業中です。これは、新しい機能（ここでは顧客向けのスケジューリングツール）を必要としていて、自作するか、購入するか、その中間の何かを行うかを決めようとしているチームの出発点です。チームが問いをどのように設定し、選択肢を議論し、情報を集めるかを示します。決定は記録されていません。

## 課題

あるサービス事業では、スプレッドシートによる手作業のプロセスで仕事のスケジュールを組んでおり、それがダブルブッキングを招いて顧客との関係を損なってきました。限られた時間内に解決策が必要であり、チームは、ツールを社内で作るか、既存のものを購入するかを決めなければなりません。

答えるべき問い：

* ツールは何をしなければならないか（要件）。そのうち不可欠なものはどれか？
* 利用できる時間内で、各ルートは要件をどれだけ満たすか？
* それを選ぶことでチームが手放すものを含め、使用期間全体を通した各ルートの総コストはいくらか？
* 要件が変わったり、選んだルートが失敗したりしたら、何が起こるか？

## 前提

それぞれの前提は検証すべきものです。

* **スケジューリングのニーズの大半は他の組織と共通で、既存の製品でカバーできる。**検証：要件を列挙し、ベンダーにそれぞれをどう満たすか示すよう求める。
* **特殊なケースは、回避策で対処できるほど小さい。**検証：発生頻度を数え、それぞれの回避策を書き出す。
* **社内のエンジニアがツールを作り、保守できる。**検証：実際に担当する人と労力を見積もり、そのために他に何をしないことになるかを尋ねる。
* **ベンダーのスケジュールは現実的である。**検証：同程度の規模のリファレンス顧客、プロジェクトが遅れた顧客も含めて話を聞く。

## 制約

* 決められた期間内に解決策が必要である。
* コミット済みの他の製品施策はスケジュールを守らなければならないので、エンジニアリングの対応力をそこから単純に取ることはできない。
* ツールは顧客データを扱うため、セキュリティとプライバシーを確認しなければならない。
* 不明、要確認：連携のニーズ、想定される成長、ベンダー契約の終了時に起こること。

## 検討した選択肢

各選択肢について、価値、コスト、タイムライン、必要な能力を見積もり、どのような証拠がチームの考えを変えるかを記録します。

* **社内で作る。**
  * 価値：組織のルールに正確に合う。ロードマップを完全に掌握できる。
  * コスト要因：ツールの全期間にわたる設計、開発、テスト、ホスティング、サポート、保守。代わりにエンジニアが作らなかったものの機会費用。
  * タイムラインの形：最初の見積もりより長くなることが多い。価値は最後に届く。
  * 必要な能力：プロダクトマネジメント、エンジニアリング、オペレーション。
* **既存の製品を購入する。**
  * 価値：速い。コストが分散される。ベンダーの改良の恩恵を受けられる。
  * コスト要因：ライセンス、導入、設定、トレーニング、連携、管理、退出。
  * リスク：要件に対するギャップ。ベンダーの変更。ロックイン。
* **製品を購入し、ベンダーにカスタム開発を委託する。**ギャップは埋まるが、時間とコストが増え、納品のリスクを伴う。
* **より小さなツールを組み合わせて構築する**（たとえばローコードプラットフォームや、既存サービスの組み合わせ）。
* **まず手作業のプロセスをつなぎの対策で改善し**、より良い決定のための時間を稼ぐ。

## 論拠

チームが想定すべき論点：

* **適合かスピードか。**遅れて届く完璧な適合は、いま得られる良い適合より悪いかもしれない。
* **中核か周辺か。**スケジューリングは事業を特徴づけるものの一部か？ そうでなければ、通常は購入が好まれる。
* **隠れたコスト。**作ることには継続的な保守が、買うことには継続的なライセンス、連携、退出がある。
* **元に戻しやすさ。**誤りと分かったとき、どちらの選択が元に戻しやすいか？

チームがコストとトレードオフを評価する方法：

1. 要件を書き、優先順位を付ける。各ルートをそれに照らして採点し、ギャップを記録する。
2. 定めた期間にわたる総所有コストを、組織自身の言葉で見積もる：一時的なコスト、継続的なコスト、社内スタッフの時間、連携、トレーニング、退出。範囲で示す。
3. 遅延のコストを見積もる：ダブルブッキングが続く期間が増えるごとの影響。
4. 最良、可能性が高い、最悪のシナリオで選択肢を比較し、要件の変更の影響をテストする。
5. 重み付けマトリクス（適合、スピード、コスト、リスク、掌握、元に戻しやすさ）とプリモーテムを使う。

## 決定

**未決定です。**これは出発点です。これを使うチームは、このセクションを自分たちの決定に置き換えてください。

決定に至るための提案：

* 誰が決め、誰が合意しなければならないかを確認する。
* 先に要件と重みで合意する。
* 上記の証拠を集め、分かったことを記録する。
* コメント用に共有し、その後決定してステータスを更新する。

## 影響

チームが購入を決めるなら、次のことが必要になります。

* 導入リードを指名し、ベンダーのスケジュールの範囲内でトレーニングを計画する。
* 非対応のケースの回避策を文書化し、その使用頻度を記録して、本番稼働後に見直す。
* カスタム開発に関する後続の決定を引き起こす条件を定義する。
* コミット済みの施策からエンジニアリングの対応力が奪われないことを確認する。
