# 主要なデータベースを選ぶ

* ステータス: コメント募集中
* 日付: 2026-03-22
* 意思決定者: CTO（要確認）
* オーナー: プラットフォームエンジニアリング責任者

概要：作業中です。これは、成長する製品の主要なデータベースを選ぼうとしているチームの出発点です。この一式の中で唯一の技術の事例であり、アーキテクチャ上の決定が、このコレクションの他の場所にあるビジネス上の決定と同じパターンに従うことを示します。チームが問いをどのように設定し、選択肢を議論し、情報を集めるかを示します。決定は記録されていません。

## 課題

現在のデータベースはスケーリングの限界に近づいており、エンジニアリングチームは、成長がまもなくその限界に達すると見ています。次の大きな製品リリースの前に、置き換えるか、別のスケーリング方法を選ばなければなりません。

答えるべき問い：

* 今日の本当の限界（読み取り、書き込み、ストレージ、レイテンシ、運用）は何か。そしてそこにどれだけの速さで近づいているか？
* どの品質が最も重要か（一貫性、可用性、レイテンシ、コスト、運用性、コンプライアンス）、その順序は？
* 今あるものをスケールさせるか、マネージドサービスに移るか、自分たちで何かを運用するか？
* どのように移行するのか。必要になったらどう再び離れるのか？

## 前提

それぞれの前提は検証すべきものです。

* **成長の予測は現実的である。**検証：過去の成長、営業と製品の計画と比較する。高い場合と低い場合を考える。
* **現在のデータベースは、費用をかければさらにスケールできる。**検証：ベンダーとチームに、どれだけ余力が残っていて、いくらかかるかを尋ねる。
* **私たちのワークロードは、水平スケールする設計に適合する。**検証：クエリとトランザクションを調べ、レコードをまたぐ強い一貫性を要する操作を探す。
* **チームは選んだ選択肢を運用できる。**検証：必要なスキルと、それを持つ人を列挙する。

## 制約

* 変更はリリース前に準備できていなければならず、段階的な移行がリリースを妨げてはならない。
* 継続的なコストは、承認された予算に収まらなければならない。
* どの選択にも、データ保護とセキュリティの義務が適用される。
* 不明、要確認：データ量、保持要件、地域要件、他のシステムとの連携、ベンダーとの約束。

## 検討した選択肢

各選択肢について、価値、コスト、タイムライン、必要な能力を見積もり、どのような証拠がチームの考えを変えるかを記録します。

* **現在のデータベースを垂直にスケールさせる**（より大きなマシンやプラン）。
  * 価値：移行リスクが最も低い。アプリケーションの変更がない。
  * リスク：得られる時間は限られる。コストが急激に上がる。
* **マネージドで水平にスケールするデータベースサービスへ移る。**
  * 価値：スケーリングと運用の多くの作業がなくなる。ベンダーのサポート。
  * コスト要因：継続的なサービス料金。移行。アプリケーションの変更。データ転送（エグレス）と退出のコスト。
  * リスク：ベンダーの機能と価格への依存。
* **セルフホストで水平にスケールするデータベースへ移る。**
  * 価値：継続的なコストが低くなる可能性。より大きな掌握。
  * コスト要因：運用スキルの構築。オンコールの負荷。ツール。アップグレード。
  * リスク：運用上のオーバーヘッドが想定より大きくなるかもしれない。
* **データ層を再設計する**（たとえばキャッシュ、リードレプリカ、パーティショニング、ワークロードの分離）ことで、現在のデータベースを延命する。
* **ワークロードごとに異なるデータベースを使う**（ポリグロット・パーシステンス）。運用するシステムが増えるという代償を伴う。

## 論拠

チームが想定すべき論点：

* **一貫性か可用性か。**CAP 定理によれば、分断された分散システムは、両方を保証できない。製品の各部分にとって、どちらがより重要か？ 多くのワークロードは遅延した一貫性に耐えられるが、そうでないものもある。
* **マネージドかセルフホストか。**より高いサービスコストと、より低い運用リスク。チームはエンジニアの時間をどう評価すべきか？
* **ロックイン。**ベンダー固有の機能を使うことで何が失われ、何が得られるか？
* **標準。**SQL（ISO/IEC 9075 で標準化）と、ベンダー固有のクエリモデルのどちらにどれだけ依存するか？

チームがコストとトレードオフを評価する方法：

1. 自分たちのワークロードでテストする：現実的なベンチマークを作り、想定負荷とピーク負荷の下で、障害シナリオも含めて各候補を測定する。
2. 定めた期間にわたる総所有コストを、組織自身の言葉で見積もる：サービスまたはライセンス料金、ホスティング、移行、エンジニアリングの時間、オンコール、トレーニング、サポート、退出。範囲で示す。
3. 重要な品質の重み付けマトリクスで候補を採点する（ISO/IEC 25010 製品品質モデルがそのための語彙を提供する）。重みへの感度をテストする。
4. 各選択肢でどれだけ時間を稼げるか、再び限界に達したときのコストはいくらかを見積もる。
5. 退出を計画する：各選択から、データとコードはどのように離れるか？

## 決定

**未決定です。**これは出発点です。これを使うチームは、このセクションを自分たちの決定に置き換えてください。

決定に至るための提案：

* 誰が決め、誰に相談しなければならないか（セキュリティ、経理、製品）を確認する。
* 先に基準と重みで合意する。
* ベンチマークの結果を含む上記の証拠を集め、分かったことを記録する。
* コメント用に共有し、その後決定してステータスを更新する。

## 影響

チームが移行を決めるなら、次のことが必要になります。

* 完全な切り替えの前に並行稼働期間を設ける、段階的な移行を計画する。
* 継続的なコストの予算を確認する。
* 後続の決定（たとえば接続プーリングやリードレプリカ）を計画する。
* 想定される退出経路を記録する。
